# File uploads

Full reference. The rules for this area are in `.claude/rules/file-uploads.md` (loaded when working on its files), with anything cross-cutting in AGENTS.md; this file holds the detail, the measurements and the history behind them.

- **PDFs are encrypted in the browser before upload** (`src/components/household-data/pdf-files.ts`: `encryptAndUploadPdf` / `downloadPdf`, over `sealBytes` / `openBytes` from `@/lib/crypto`). The stored object is `households/<householdId>/<apartmentId>.pdf.enc` — AES-256-GCM ciphertext with AAD `"<householdId>:pdf:<apartmentId>"` when encryption is on, the raw PDF bytes with `iv: null` when off. The server stores and serves it as `application/octet-stream` and never learns which. The apartment envelope carries `pdf: { path, iv } | null`.
- **Transport**: `uploadEncryptedFile(bytes, apartmentId)` in `src/lib/upload-pdf.ts` probes `GET /api/files/upload-token`; when Blob is enabled (`BLOB_READ_WRITE_TOKEN`, auto-set by Vercel) it uploads client-direct to Vercel Blob with a token scoped to that path, otherwise it multipart-POSTs to `/api/files` (local-disk fallback via `src/lib/storage.ts`). Files larger than ~4.5 MB **must** take the Blob path — serverless routes hit the body limit — which is why the probe exists.
- **Reading back**: `/api/pdf/[...path]` (Blob) and `/api/uploads/[...path]` (local disk) stream the ciphertext to a signed-in member of the owning household; the client decrypts and opens a `blob:` URL. There is no server-side "view PDF" any more.
- **Replacing a file** (#413): an attach or replace on the apartment page uploads under a revision name (`<id>[.k<v>].r<12 hex>.pdf.enc`, validated by `PDF_REVISION_PATTERN` in `src/lib/pdf-file-name.ts`), and `DELETE /api/files` with `{ path }` removes the old one: any member, any file of their own household, a path outside it 400. Same trust as deleting an apartment with its `pdfPath`. Rotation renames to `pdfFileName(id, next)` and drops the revision.
- **Extraction** goes through `POST /api/process/parse-pdf` (multipart, plaintext PDF, Gemini) — the privacy exception above. The PDF the user uploads is sent there *and* encrypted for storage; the server keeps only the ciphertext.
- **Reading a PDF is capped at 4.5 MB on Vercel (#438)**, because that is Vercel's function body limit and extraction has no Blob path: the PDF goes in the request body. `readLimits()` sends the cap to the browser as `limits.pdfReadMaxBytes` (`VERCEL_PDF_READ_MAX_BYTES`, a 16 KiB margin under 4.5 MB, when `VERCEL` is set; otherwise `parsePdfMaxBytes()`, 20 MB, so self-hosters keep it). `parsePdf` refuses a larger PDF before sending anything, reason `too_large`, and a 413 from either Vercel or the route maps to the same reason. The PDF is still stored; the add page keeps it unread like a PDF refused for want of credit, the apartment page shows `PdfTooLargeNotice` (how to make the PDF smaller, five languages), and Reprocess opens the PDF before charging so a too-large one spends nothing. **Decided by the owner: no trimming in the browser and no plaintext upload to Blob to get around the limit**; the second would break the privacy section's "in memory, never stored".
- Deleting an apartment deletes its file (`deleteStoredFile` in `src/lib/storage.ts`, called by `DELETE /api/apartments/:id` with the `pdfPath` the client sends, validated to belong to the household).
