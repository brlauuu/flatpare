# Tests

Full reference, moved verbatim from AGENTS.md. The always-on rules for this area are summarised in AGENTS.md; this file holds the detail, the measurements and the history behind them.

- **Vitest, not Jest.** Don't reach for Jest patterns — they break here.
- Config: `vitest.config.mts`. Setup: `src/test-global-setup.ts` (builds the migrated template database once) and `src/test-setup.ts` (per test file — copies the template and points `LOCAL_DB_URL` at the copy).
- Tests live in co-located `__tests__/` directories next to the source.
- `npm test` runs once; `npm run test:watch` watches. CI runs `npm run test:coverage`.
- **Test files run in parallel, each against its own database** (#202). `src/test-global-setup.ts` migrates `data/test-template.db` **once**, and `src/test-setup.ts` copies it to `data/test-<pid>.db` per file, pointing `LOCAL_DB_URL` at the copy before any import (`src/lib/db` reads that var at module load). 164.9s → 51.1s.
  - **Do not key the per-file database on `VITEST_WORKER_ID`** (the shape the issue originally proposed). Under `isolate: true` vitest spawns a fresh process per test *file*, so neither that id nor `process.pid` is stable across files — both were measured producing 101 databases, one per file, each running the whole migration chain. The pid is used only to *name* the copy, which needs to be unique among concurrently-running files and nothing more.
  - `globalSetup` uses `applyMigrations`, **not** `runMigrations`: the latter memoizes into a module-level promise, and priming it makes `migrate.test.ts`'s own call a no-op.
  - **testing-library's `asyncUtilTimeout` is at its 1000ms default**, deliberately. It was raised to 5000ms in #226 to hide flakes and to 2000ms as a margin; #227 removed the three actual races, and the default was restored to prove they were gone. **If a test starts flaking, do not raise it** — find the pending work the assertion is racing and give it an anchor.
  - **Test shapes that flaked under parallelism and must not come back** (#227, #442): (a) waiting on the DOM while asserting on a variable populated by a `useEffect` — the effect runs *after* commit, so the wait can resolve a render early; wait on the value you assert on (`waitForContext` in `household-data-provider.test.tsx` is the pattern). (b) `getByRole` against a listbox, dialog or popover that opens asynchronously — use `findByRole`. (c, #442) anything that appears only after an IndexedDB call (the share stash, fake-indexeddb in tests): `findBy*`'s 1000ms covers the call itself, which outlasted it under the loaded coverage run, and a `waitFor(async () => await readShare(...))` puts a read inside every attempt. `share-intake.test.tsx` records the real stash functions with `vi.fn(actual.x)` and awaits the page's own calls (`stashSettled`, `stashWritten`); do the same. And paste, do not type, long values in a test that is not about typing (`edit-flow.test.tsx`).
  - A `.not.toHaveBeenCalled()` after an `await` is fine when nothing is still pending; it is racy only when the denied call could be **deferred** (a `setTimeout` navigation, say). If you add deferred work, give the assertion an anchor rather than trusting ordering.
- `npm run typecheck` (`tsc --noEmit`) is enforced in CI alongside lint. `next build` does not typecheck test files, so this is what catches type errors in `__tests__/`.
- **End-to-end tests live in `e2e/` and are NOT part of `npm test` or CI** (`npm run test:e2e`, Playwright, config at `playwright.config.ts`). They talk to the **real Stripe test API**, because the unit tests mock `checkout.sessions.create` and therefore accept any session shape — three defects shipped past them and were caught only by a hand-run checkout (#238). Without a `sk_test_...` key every spec **skips**, so an unconfigured run is a no-op rather than a red build; `tsc --noEmit` still typechecks them, since `tsconfig.json` includes `**/*.ts`. Read `e2e/README.md` before adding one — particularly the part about the suite delivering its own signed webhook rather than depending on `stripe listen`.
- **Coverage thresholds are enforced in CI** via `vitest.config.mts`: lines ≥ 80, statements ≥ 80, functions ≥ 78, branches ≥ 75. Since #203 they apply to **every source file**, not only those a test imports — `coverage.include` is `src/**/*.{ts,tsx}`, so a wholly untested new file *is* pulled into the average and can trip the floor. There is real headroom above every floor; run `npm run test:coverage` for the current numbers rather than trusting a figure written down here, which drifts with every merge. **Do not reach for `coverage.all`**: it was removed in vitest 3 and was measured to change nothing either way; `include` is the only knob that matters.
- Excluded from the coverage count, and only these: `src/components/ui/**` (shadcn primitives — vendored, re-emitted by the CLI), `src/lib/db/schema.ts` (Drizzle table declarations, no executable logic), `src/test-setup.ts` / `src/test-global-setup.ts` (the harness itself, in no bundle), `src/types/**` + `**/*.d.ts` (ambient declarations), and `**/__tests__/**` (fixtures and helpers — added in #254; `coverage.include` had been grading them as product code, so a fixture's unused branch counted against the floor). Don't write tests targeting those files. Everything else stays counted **including `error.tsx` and the MapLibre `*-map-inner.tsx` components**, which report 0% (`src/app/layout.tsx` and `src/instrumentation.ts` have tests now) — that is honest signal about shipped code, not noise to exclude. #254 re-confirmed that for the (then Leaflet) map inners specifically and wrote the reasoning into `vitest.config.mts`, so it does not have to be re-litigated from this file. (The signed-in layout is no longer 0%: #251 covered the four that existed then, and `signed-in-layouts.test.tsx` now covers the one shared layout that replaced them in #302.)
  - Reading the report: `src/lib/session.ts` shows 0% despite `requireHousehold` being used everywhere, because the route suites `vi.mock("@/lib/session")` wholesale so the real module never executes. A 0% row means "not executed by any test", not necessarily "untested behaviour".
