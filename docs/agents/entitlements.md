# Entitlements (E5)

Full reference, moved verbatim from AGENTS.md. The always-on rules for this area are summarised in AGENTS.md; this file holds the detail, the measurements and the history behind them.

- **`MAX_MEMBERS` and `MAX_APARTMENTS`**, read by `readLimits()` (`src/lib/limits.ts`) via the shared `readOptionalPositiveInt` (`src/lib/env-int.ts`). **Unset or empty means unlimited** — the self-hoster default, called out in #187 as a must-not-regress and covered by dedicated tests at every layer. A value that is not a positive integer throws `EnvConfigError` rather than being coerced.
- **There is no tier dimension, and `households.tier` is NOT read by E5.** The hosted deployment has no free tier (everyone pays from day one) and self-hosters set their own values, so the spec's "5 and 20, lifted to 10 and 100 for a paid account" describes a model that was not adopted — the spec's E5 section carries a superseded note. `households.tier` is read by **nothing** — not E5, not E6 — and is kept only so the column need not be added later. If you find yourself adding a `householdId` argument to `readLimits()`, that is the decision being reversed; make it deliberately.
- **Three enforcement points, all server-side:**
  - `createApartmentRow` (`src/lib/apartments-store.ts`), which `POST /api/apartments` delegates to. The cap is a conditional `INSERT ... SELECT ... WHERE (count) < max` — **one atomic statement, not a count-then-insert**, so concurrent creates cannot both take the last slot. Do not "simplify" it back into a `db.transaction`: parallel transactions on the libSQL connection fail with `SQLITE_BUSY: cannot commit transaction — SQL statements in progress`. `createLocation` (`src/lib/locations.ts`) enforces `MAX_LOCATIONS` the same way since #225, with a 10-way concurrency test.
  - `createInvitation`, which counts members **plus still-pending invitations** — checking members alone enforces nothing, since four members and ten pending invitations is fourteen members. A courtesy check, so an owner is not offered an invite that will 409.
  - `acceptInvitation`, inside its existing transaction, before the membership insert. **This is the real enforcement point** — time passes between send and accept. Throwing there rolls back the status update that claimed the invitation, so a refused accept leaves the row **pending** and the invitee can retry once a slot frees.
- **Reaching the client:** `limits` travels the same path as `identity` — `readLimits()` in the shared signed-in layout (`src/app/(app)/layout.tsx`), a server component, passed as a prop to `HouseholdDataProvider`, exposed as `useHouseholdData().limits`. **Never read `process.env.MAX_*` in a `"use client"` file.** The test fixture defaults both axes to `null`, so a page test only passes `limits` when it cares.
- **UI counters render only when a limit is configured** (`src/app/apartments/page.tsx`, `src/components/household-settings.tsx`). A self-hoster with no vars set must not see a counter implying a cap that does not exist; both have a test asserting its absence.
