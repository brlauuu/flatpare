# Database

Full reference, moved verbatim from AGENTS.md. The always-on rules for this area are summarised in AGENTS.md; this file holds the detail, the measurements and the history behind them.

- **Drizzle ORM** (`drizzle-orm`, `drizzle-kit`). Schemas in `src/lib/db/schema.ts`, migrations in `drizzle/`.
- Connection via **libSQL** (`@libsql/client`) — Turso in cloud mode, local SQLite file otherwise.
- Scripts: `npm run db:generate`, `db:migrate`, `db:push`, `db:studio`.
- Relevant env: `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, `LOCAL_DB_URL` (defaults to `file:./data/flatpare.db`; each test *file* points at its own `file:./data/test-<pid>.db`, see Tests).
- **Which database is live is decided by truthiness of `TURSO_DATABASE_URL`** (`resolveDbTarget` in `src/lib/db/target.ts`), and `.env.local` sets it — so **`npm run dev` writes to a remote Turso database** unless you clear it. Since 2026-09-19 that is `flatpare-dev`, not production, but it is still shared state; the `[db]` boot line names the host. The presence of `data/flatpare.db` on disk means nothing. To run against the local file: `TURSO_DATABASE_URL= npm run dev` (an explicitly *empty* value overrides `.env.local`, because the check is truthiness, not presence).
- **The app now says which one it picked**, once, at boot: `src/instrumentation.ts` logs `[db] Turso (cloud) — <host>` or `[db] local file — <url>`, and adds a `WARNING` when `NODE_ENV` is anything but `production` while the target is cloud. Only the host is ever printed, never the URL's query string or the auth token — `resolveDbTarget` is also what builds the client, so the logged line cannot drift from the connection actually opened.
- **Migration 0013 stamps the encryption mode** into the `settings` table on first boot (`stampEncryptionMode` in `src/lib/db/migrate.ts`) and throws on every later boot if `FLATPARE_ENCRYPTION` disagrees with the stamp. Changing mode means a fresh database. Tests that need a specific mode use `applyMigrations(client, { encryptionMode })` on an in-memory client.
- **Upgrading a database that already holds rows requires choosing the encryption mode by hand.** The first stamp is where the one-way decision is taken, so `stampEncryptionMode` refuses to take it for you: if `apartments` is non-empty and `FLATPARE_ENCRYPTION` is unset (or empty), boot fails with an error naming both choices. Set it explicitly first — `off` keeps the existing rows readable, `on` starts encrypting and makes them unreadable to a later release — and note the choice is permanent for that database (changing it means a fresh database, or exporting each household and importing it into the new one, see Export and import). A fresh/empty database is unaffected and still defaults to `on`.
- **Migration 0014 (E3) dropped the plaintext data tables** (`apartments`, `ratings`, `locations_of_interest`, `apartment_distances`) and created three envelope tables (`apartments`, `ratings`, `locations`) keyed by client-minted UUIDs. There is no data migration: `preflightEncryptedModelMigration` in `src/lib/db/migrate.ts` throws before 0014 runs if any of the four old tables holds rows, naming them, so a pre-E3 database has to be wiped by hand first (the hosted one was wiped before deploying, same posture as E1). The four legacy runtime backfills (`ensureListingUrlColumn`, `reconcileHasWashingMachine`, `backfillShortCodes`, `migrateLocationsOfInterestBackfill`) are gone with the columns they patched; `preflightTenancyMigration` stays. Since #211, `scripts/vercel-build.mjs` runs `scripts/migrate.ts` (→ `runMigrations`, via `npx tsx`) at build time, so the Vercel build takes the same preflights as the boot path; `drizzle-kit migrate` is no longer used there, having bypassed them and swallowed the error.
- **Migration 0015 adds a unique index on `users.email`** (`users_email_unique`, case-sensitive). Auth.js already assumed one row per address — its OAuth flow calls `getUserByEmail` before creating a user and answers `OAuthAccountNotLinked` on a hit — but nothing enforced it, so the credentials provider's select-then-insert could race two rows onto `self-hosted@flatpare.local` and split a self-hosted deployment into two households with no merge UI (#200). The index is deliberately **not** `COLLATE NOCASE`: `getUserByEmail` is a case-sensitive lookup, so a NOCASE index would turn a case-differing second provider into an opaque constraint failure instead of the clean `OAuthAccountNotLinked` path. `preflightDuplicateUserEmails` in `src/lib/db/migrate.ts` throws before 0015 runs if the database already holds duplicates, naming the addresses and the colliding user ids — they cannot be merged automatically, since each one owns a separate household.
- **Migration 0016 (E4) adds `process_usage`** — the rate-limit counter keyed `(household_id, endpoint, window_start)`. No data migration, no preflight: it is a new empty table. See the Blind proxies (E4) section for why it holds no request content.
- **Migration 0017 (E6) adds the apartment credit counters** — `households.apartment_credits_granted` and `apartments_ever_added`, both defaulting to 0. No data migration, no preflight: existing households start at zero granted, which with billing off is never read. See Apartment credits (E6).
- **Migration 0018 (E6) adds `payments`** — the grant ledger, keyed by the Stripe **event id** so a webhook redelivery cannot grant twice. New empty table, no preflight.
- **Migration 0019 (#239) adds `beta_passes` and `beta_pass_redemptions`** — the under-development gate's door. New empty tables, no preflight. See Public access gate and beta passes.
- **Migration 0020 (#240) adds `beta_pass_redemptions.granted_at`** — the once-only mark for the credit grant. Nullable, no data migration, no preflight.
- **Migration 0021 (#219) adds the data-key version**: `households.key_version` (default 1), `households.rotation_due` (default false) and `household_key_wraps.key_version` (default 1). No data migration: everything that exists is version 1. See Data-key rotation under Encryption.
- **Migration 0024 (#192) adds the co-owner recovery-kit notice**: `households.recovery_created_by` (who made the current kit; null for kits made before it) and `household_members.recovery_kit_seen_at` (when that owner dismissed the notice). Nullable, no data migration, no preflight. The owner role itself needed nothing: `household_members.role` already allowed any number of owners. See Co-owners.
- **Migration 0025 (#190) adds `apartment_drafts`** — links saved to add later: `id`, `household_id`, `created_by`, `envelope`, `created_at`. New empty table, no preflight. See Drafts (#190).
- **Migration 0026 (#413) adds `apartment_charges`** — which apartments have had their first processing paid for: `household_id`, `apartment_id` (the client-minted id, no foreign key, because a PDF is read before its row exists), `charged_at`. It also inserts a row for every apartment that already exists, since those were paid for when they were created (the old rule). No preflight. See Processing and credits (#413).
- **Migration 0027 (#413) adds `credit_spends`** — one row per spent credit: `id`, `household_id`, `kind` (`first`, `reprocess`, `recompute`), `spent_at`. New empty table, no preflight. It is the host's log for cross-checking calls against payments, see Processing and credits (#413).
- **Migration 0029 (#492) adds `credit_codes` and `credit_code_redemptions`** — the operator's codes that add credits to a household, and which household redeemed which (primary key on both). New empty tables, no preflight. See Apartment credits.
- **Migration 0028 (#476) adds `feedback_days`** — `day` (UTC, `YYYY-MM-DD`) and `count`, the site-wide cap on feedback emails. New empty table, no preflight. A migration test pins the two columns: feedback itself is never stored. See Email.
- **Migration 0022 (#301) adds `beta_requests`** — the landing page's beta-invite requests: `id`, `email` (unique, stored lowercased), `created_at`, and nothing else about the person. New empty table, no preflight. See Landing page.
- **`db.transaction` retries on `SQLITE_BUSY`** (#225, `retryOnBusy` in `src/lib/db/busy-retry.ts`, wrapped once in `src/lib/db/index.ts`). Each local libSQL transaction takes its own connection and starts with `BEGIN IMMEDIATE`, so a concurrent second one was refused at once (1 of 10 got through). **Do not reach for the client's `timeout` (busy timeout) instead**: the driver is synchronous, its wait blocks the only Node thread, the lock holder cannot commit, and every waiter times out — measured, 9 of 10 failed after 5s each. The retry waits with `setTimeout`, jittered, for up to 3s, then rethrows. Retrying a whole transaction is safe because drizzle rolls back on every failure; **keep transaction bodies to the database** (no email, no fetch), or a retry repeats the side effect. Single-statement writes (`createApartmentRow`, `createLocation`, the credit and beta-pass counters) need no transaction and stay that way. **On Turso the retry does not fire** (#368, measured 2026-10-22 on a throwaway database): the server queues concurrent write transactions itself. With the retry bypassed, 10 and 25 concurrent transactions all committed, from one client and from one client per transaction alike (the shape of separate Vercel instances), at a steady ~220ms each, i.e. one after another. `busy-retry.test.ts` and `locations.test.ts` pass against it unchanged. So the retry is for the local file (self-hosters, tests); keep it, it costs nothing on Turso.
