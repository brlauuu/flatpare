# Navigation and the signed-in shell (#302)

Full reference. The rules for this area are in `.claude/rules/navigation.md` (loaded when working on its files), with anything cross-cutting in AGENTS.md; this file holds the detail, the measurements and the history behind them.

- **Every signed-in section lives in the route group `src/app/(app)/`** — `apartments`, `compare`, `household`, `settings`, `guide` — under **one** layout, `src/app/(app)/layout.tsx`. A route group adds nothing to the URL. That layout is the only place that awaits `auth()`, runs `requirePurchase` and mounts `NavBar`, `CryptoGate` and `HouseholdDataProvider`. Anything written before #302 that says "the four signed-in layouts" means this file.
- **Why one layout:** there used to be four near-identical ones. Next.js blocks a navigation until a layout that reads the session has rendered, and it does that again whenever a navigation crosses a layout boundary, so every section switch waited on the server with nothing on screen, then remounted both providers and re-downloaded and re-decrypted every row. A shared layout is not re-rendered on client navigation and its providers stay mounted.
- **Do not add an `async` layout, or a provider, to a section.** The per-section `layout.tsx` files are synchronous width wrappers (`SectionWidth`, 62rem); `compare` has none because its table takes the full window. `signed-in-layouts.test.tsx` reads every nested layout under `(app)` and fails on `async`, `await`, or a provider import. A new signed-in section goes inside `(app)`; a page that must not require an unlocked key (like `/billing`) goes outside it.
- **The shared layout's awaits run on a full page load only**, not per navigation. That is sufficient because `src/proxy.ts` authenticates every request and every data route re-checks membership, but it means the layout is not where a per-navigation check can live.
- **`src/app/(app)/loading.tsx` is what makes a click respond immediately.** Every route here is dynamic, and without a loading file Next.js prefetches nothing for a dynamic route. `NavLabel` in `src/components/nav-bar.tsx` (`useLinkStatus`) dims the clicked link for the case where the loading state has not been prefetched yet.
- **The store refreshes in the background on a section switch** (`load(true)` in `household-data-provider.tsx`, keyed on the first path segment). Before #302 the remount was the only way another member's changes arrived without a reload; this keeps that without the wait. A background refresh never sets `status` back to `loading`, is **dropped if any write committed while it was in flight** (it may predate the write), and a failure keeps what is on screen. Moving within a section (list to detail) does not refresh, as before.
