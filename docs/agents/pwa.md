# PWA

Full reference, moved verbatim from AGENTS.md. The always-on rules for this area are summarised in AGENTS.md; this file holds the detail, the measurements and the history behind them.

- `src/app/manifest.ts` is the web app manifest (Next's `MetadataRoute.Manifest`, served at `/manifest.webmanifest`) — not a static file in `public/`.
- Icons in `public/` are generated from `public/flatpare_logo.svg` by cropping the square mark out of the wordmark. `icon-maskable-512.png` keeps the mark inside Android's safe zone; `apple-touch-icon.png` exists because iOS ignores the manifest's icons.
- `theme_color` / `background_color` mirror `--primary` / `--background` (light theme) in `globals.css`; `manifest.test.ts` reads the stylesheet and fails if they drift. The root layout's viewport `themeColor` is `--background` per theme.
- **There is a service worker, and it only receives shares** (#190, `public/sw.js`). It answers exactly one request: a `POST /share-target` on this origin (the phone's share sheet). It caches nothing: no `caches`, no pages, no responses, no offline shell, and every other request gets no `respondWith`, so the app behaves as it does without a worker. The one thing it writes is the share stash below. The original objection (an offline shell cannot show real data under E2EE, and a stale cached shell is hard to debug remotely) does not apply, because nothing is cached. A GET to `/share-target`, a POST elsewhere and a request to another origin are left alone; `service-worker.test.ts` pins that.
  - **"On this origin" is the request's URL, not who sent it.** Any website can auto-submit a form to `https://flatpare.com/share-target`, with a link, a title or a PDF, and the worker stashes it like a real share: it cannot tell the share sheet from a forged form (`referrer` can be suppressed, `Sec-Fetch-*` is not visible to it). The defence is the person's tap: **nothing in the stash is acted on without one.** The add page asks first (`ShareConfirm`: "Add the PDF you shared?" with the count, or "Add an apartment for the link you shared from <host>?"), and processes nothing, calls no paid API and adds nothing until Add; Discard deletes the entry. The pick-up prompt's Add is itself that tap and passes `&confirmed=1`, which cannot be forged into a skip: the id is a random UUID minted in this browser that no other site learns, and an unknown id only says the share did not arrive. A forged entry that is never confirmed expires after 24h.
  - **The stash** is IndexedDB database `flatpare-share`, store `shares`, in the browser only. The worker writes `{ id, createdAt, title, text, url, files, dropped }` (PDFs kept, other files counted in `dropped`) and answers 303 to `/apartments/new?share=<id>`; if the write fails it redirects to `?share=unavailable`, never an error page. Entries expire after 24h and are pruned on every open. `src/lib/share-stash.ts` is the page's side (a leaf); a worker cannot import it, so the layout (name, version, store, TTL) is repeated in `sw.js` and `service-worker.test.ts` fails if they drift.
  - **No-worker fallback:** `POST /share-target` (`src/app/share-target/route.ts`) answers 303 to `?share=unavailable` and **never reads the body** or logs anything, because a shared PDF has nowhere safe to go on the server. It happens on the first visit before the worker is active, or when registration failed.
  - **Registration** is `ServiceWorkerRegistrar` in the root layout, so the landing page registers too: Android offers a share target only for an installed app, and installing can precede sign-in. Failure (no support, private window) is swallowed. `next.config.ts` serves `/sw.js` with `Cache-Control: no-cache` so a changed worker is picked up on the next visit.
  - **Intake** is `use-share-intake.ts` on `/apartments/new?share=<id>`: once confirmed (above), PDFs go into the normal add flow, a link (from `url`, or the first http(s) URL in `text`) becomes an unprocessed apartment, which the page then opens (#413), non-PDFs are dropped and said so. **It acts only once `useHouseholdData().status === "ready"`**: the worker's redirect (and the unlock) is a full page load, and an apartment committed while the store's first load is in flight is overwritten by that load's answer, so the shared link would vanish from the list. The entry is deleted only after every item saved or the apartment was created (`finishShare`), so a reload during review offers it again. **After a partial save of a multi-PDF share the entry keeps only the files that did not save** (`settleShare` → `keepShareFiles`; items map to files in the order `processFiles` received them, and discarded items count as handled), so reopening it does not add, and pay for, the saved ones twice. The same hook consumes `launchQueue` for `file_handlers`.
  - **Pick-up prompt:** a share that arrives signed out is redirected to `/` by the proxy but stays stashed; one that arrives while locked keeps its URL, and the add page handles it directly once unlocked. `PendingSharePrompt` (inside the household provider, so only when unlocked) offers the newest entry. It re-reads the stash on every path change, because the shared layout stays mounted and the add page deletes its entry just before navigating away; a read at load would offer a consumed share.
  - **Sign-out clears the stash** (`clearShares` in `nav-bar.tsx` and `src/app/invitations/page.tsx`, before `signOut`).
  - **`file_handlers`** (open a PDF with the installed app) is desktop Chrome and Edge only. **Android does not honour it**, measured 2026-10-30 on the owner's phone (Samsung, Android, Chrome WebAPK at 0.30.1): `cmd package query-activities -a android.intent.action.VIEW -t application/pdf` does not list the Flatpare WebAPK, while `...SEND -t application/pdf` does. So on Android a PDF arrives through `share_target` (share it to Flatpare), never "open with"; do not claim otherwise in the guide.
  - **Install help** (`src/components/install/`): "Install app" in the user menu and a phone-only tip on the Apartments list, dismissed for good in `localStorage` (`flatpare_install_hint_dismissed`, wrapped in try/catch; in memory when storage is refused). Which one shows is `installState` (`src/lib/install-state.ts`, pure): `installed` (display-mode standalone, `navigator.standalone`, or `appinstalled`) shows nothing; `prompt` calls the browser's saved `beforeinstallprompt` event, usable once; `ios` (iPhone, or an iPad reporting itself as a Mac with a touch screen) opens a how-to dialog, since iOS never offers a prompt; `none` shows nothing. **The `beforeinstallprompt` listener is added when `install-prompt.ts` loads, not in an effect**: Chrome fires it once and can do so before hydration. The guide's "On your phone" section describes all of this in five languages; change both together.
  - **Known limit: opening a PDF with the app while signed out loses the file, without saying so.** A launch goes through `launchQueue`, not the worker, so nothing is stashed; the proxy sends the window to `/` and the file is gone. Desktop only, and common enough with the 24h session cap. Not fixed: whether `launchQueue` still delivers after a proxy redirect could not be verified here.
