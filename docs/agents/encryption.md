# Encryption (E2)

Full reference. The rules for this area are in `.claude/rules/encryption.md` (loaded when working on its files), with anything cross-cutting in AGENTS.md; this file holds the detail, the measurements and the history behind them.

- **Mode:** `FLATPARE_ENCRYPTION=on|off`, read once server-side by `readEncryptionMode()` (`src/lib/encryption-mode.ts`); unset is `on`, anything else fails boot. Reaches the client only as the `mode` prop of `<CryptoProvider>`, passed by the server component `src/components/crypto/crypto-gate.tsx` from the shared signed-in layout (`src/app/(app)/layout.tsx`). Never read `process.env.FLATPARE_ENCRYPTION` in a `"use client"` file.
- **Layering rule, enforced by ESLint (`cryptoLayering` in `eslint.config.mjs`):** `crypto.subtle`, `globalThis.crypto.subtle`, `window.crypto.subtle`, `crypto.getRandomValues` and `hash-wasm` may appear only under `src/lib/crypto/**`, and submodule imports (`@/lib/crypto/kdf`, `@/lib/crypto/a/b`) are banned at every depth outside it. Everything else imports named functions from `@/lib/crypto`. Tests under `src/lib/crypto/__tests__/` are inside the allowed tree and their helpers stay importable.
  - **Hand-verified 2026-09-06** with `npx eslint --stdin --stdin-filename <path>`, five probes, all observed as stated: (1) `crypto.subtle` in `src/lib/probe.ts` → error `no-restricted-syntax` ("crypto.subtle is only allowed under src/lib/crypto/"); (2) `crypto.getRandomValues(new Uint8Array(8))` in `src/lib/probe.ts` → error `no-restricted-syntax`; (3) `await import("hash-wasm")` in `src/lib/probe.ts` → error `no-restricted-syntax`; (4) `import { deriveKek } from "@/lib/crypto/kdf"` in `src/lib/probe.ts` → error `no-restricted-imports`; (5) the same `crypto.subtle` line in `src/lib/crypto/probe.ts` → **no error** (inside the allowed tree). The import pattern was probed separately: `@/lib/crypto` allowed, `@/lib/crypto/kdf` banned, `@/lib/crypto/__tests__/params` allowed, `@/lib/crypto/sub/deep` banned.
  - **E3 extends the layering one level up:** `src/lib/household-data/**` is the pure data layer (types, zod schemas, wire shapes, ids, codec, derivation, enrichment planners, maintenance planners, concurrency helper). It imports nothing outside itself except `@/lib/crypto`. `src/components/household-data/**` is the only place that combines the codec with `fetch` (`api-client.ts`, `process-client.ts`, `pdf-files.ts`, `enrichment.ts`, `household-data-provider.tsx`). Route handlers import types from `@/lib/household-data/wire` and nothing else from that tree. Pages import `useHouseholdData` and the plaintext types; they never import the codec or call `fetch` for household data.
- **Key material:** RSA-OAEP-3072 member key pair (private half wrapped under an Argon2id-derived AES-256-GCM KEK, `member_keys`), one AES-256-GCM household data key wrapped to each member's public key (`household_key_wraps`), and a recovery kit (data key wrapped under a KEK derived from a 25-character base32 code, `households.recovery_*`). Stored keys on the device are non-extractable `CryptoKey`s in IndexedDB (`src/lib/crypto/store.ts`, memory fallback when IndexedDB is unavailable). Wrapping needs an extractable key, so flows that wrap unwrap a transient extractable copy and never persist it.
- **Server store:** `src/lib/member-keys.ts` (status, setup, wraps, reset, recover, recovery regeneration; all state errors are `CryptoStateError` with 400/403/409) behind `src/app/api/crypto/*`. Every handler: `requireHousehold()` → `requireEncryptionOn()` (409 when off; `status` is the one route that answers in off mode) → `assertMembership` → `parseBody`. Shared error mapping lives in `src/lib/api-route.ts` (`apiErrorResponse`, `parseBody`); `ApiError` in `src/lib/api-error.ts` has no imports so any layer can throw it.
- **Client:** `src/components/crypto/flows.ts` is the only place that sequences crypto + fetch (`src/components/household-data/rotation.ts` borrows its helpers for the one flow that also needs the codec, #219); `crypto-provider.tsx` derives `off | needs-setup | pending-wrap | needs-household-key | locked | unlocked` from `GET /api/crypto/status` plus the device store and renders the matching screen instead of the page. Adding a screen means adding it to `src/components/crypto/__tests__/no-import-cycle.test.ts`. Pages under the shared signed-in layout may assume `useCrypto().keys.dataKey` is non-null when `state === "unlocked"` — E3 builds on that.
- **Argon2id runs in a Web Worker** (#396): `deriveKekBytes` (`src/lib/crypto/kdf.ts`) starts `kdf-worker.ts` for each derivation, because on the main thread one derivation froze the page for ~0.5s on a desktop and ~2s on a slower phone. The derivation itself lives in `argon2.ts`, shared by both sides. Where no worker can run (jsdom, the server) or it fails to start or answer, it derives on the main thread as before, so the result never differs and nothing can hang. Turbopack compiles the worker from `new Worker(new URL("./kdf-worker.ts", import.meta.url), { type: "module" })`; keep that literal shape, or it is copied as a raw asset instead and every unlock silently falls back.
- **Argon2id parameters are pinned by test** (`src/lib/crypto/__tests__/kdf.test.ts`): password "correct horse battery staple", salt `00..0f`, 65536 KiB / 3 / 1 → a fixed 32-byte digest. Changing `DEFAULT_KDF_PARAMS` must change that vector on purpose. Tests derive with `TEST_KDF_PARAMS` (1024 KiB / 1 / 1) to stay fast.
- **Tests take member key pairs from a pool, not the generator** (#361): `src/test-global-setup.ts` generates `POOL_SIZE` RSA-3072 pairs once per run and provides them; `takeMemberKeypair()` (`src/lib/crypto/__tests__/keypair-pool.ts`) imports one, round-robin, and `flows.test.ts` swaps it in for `generateMemberKeypair` with a partial `vi.mock`. Each real generation costs 250–900ms and was what pushed crypto tests past the 15s timeout under the parallel coverage run; the four files went from ~83s of file time to ~5s. Only `keys.test.ts`'s RSA-OAEP-3072 test still calls the real generator. A new test needing a key pair takes one from the pool; one needing more than `POOL_SIZE` distinct pairs raises the size.
- **Key fingerprints (#218)**: the Household page shows every member's public key as 8 emoji (`fingerprint` in `src/lib/crypto/fingerprint.ts`, SHA-256 of the SPKI, first 8 bytes into `FINGERPRINT_EMOJI`). **The set's order is part of the format** and pinned by a vector in `fingerprint.test.ts`, like the Argon2id one: reordering it changes every member's code. **Your own row is fingerprinted from `StoredKeys.publicKey`, never from `GET /api/household/members`** — every flow that saves keys writes it, `runUnlock` by working it out from the private key the passphrase opened (`publicKeyFromPrivate`, a transient extractable unwrap). Records saved before #218 lack it and the row asks for a lock and unlock; do not add a fallback to the server's copy, that would make a substituted key fingerprint as itself. `flows.test.ts` and `household-settings.test.tsx` pin both halves.
- **Accepted limits** (details in `docs/security-notes.md`): an actively malicious host could substitute a public key during a wrap; XSS on the origin can use (not export) unlocked keys; a removed member keeps whatever ciphertext they fetched before removal (rotation, below, closes everything after).
- **Data-key rotation (#219)** — design in `docs/superpowers/specs/2026-09-19-key-rotation-design.md`. `households.key_version` names the current data key; every wrap records the version it holds and every v1 envelope records the version that sealed it (`k`, absent = 1). **The server refuses any envelope write not sealed under the current version** (`requireCurrentKey` in `src/lib/api-route.ts`, `409 { error: "Stale key", keyVersion }`, applied in all five write routes), so a device holding an old key cannot write rows nobody else can read. Rotation is client-side and owner-driven: `runRotateDataKey` (`src/components/household-data/rotation.ts` — beside the store because it needs the codec and the PDF helpers; it borrows `api`/`post`/`makeRecoveryKit` from `src/components/crypto/flows.ts`) re-seals every row and PDF under a fresh key, wraps it to every member with a public key, mints a **new recovery kit** (the code changes — see security-notes for why), and commits through `POST /api/crypto/rotate` → `rotateHouseholdKey` in `src/lib/member-keys.ts`, one transaction, all or nothing: version match, wrap set = members with keys with current public keys, row sets = the household's rows with apartment versions current, every envelope `k = next`. `envelope: null` keeps a corrupt row untouched. PDFs go to `<id>.k<version>.pdf.enc` (`src/lib/pdf-file-name.ts`) **before** the commit; the old file is deleted after it.
  - **Removal marks `rotation_due`; the settings page rotates right after a successful removal** and hands the new code to `showRecoveryKit`. If that fails the household is untouched and the owner sees a warning with a "Rotate household key" button until it lands. The button lives in `src/components/household-settings.tsx`, **not** `encryption-settings.tsx`, because `src/components/crypto` must not import from `src/components/household-data`.
  - **Other devices re-key silently.** `StoredKeys.keyVersion` is compared with `status.wrapKeyVersion` in `CryptoProvider.refresh()`; when behind, the wrap is adopted with the private key already on the device. The provider re-reads status once a minute while unlocked (`WRAP_SWEEP_MS`), and `apply` keeps the keys object's identity when nothing changed so that beat does not make the household store reload. A write answered `Stale key` triggers a refresh and surfaces as "please try again" (`STALE_KEY_MESSAGE`).
  - Tests: `src/lib/__tests__/member-keys.test.ts` (transaction rules), `src/components/household-data/__tests__/rotation.test.ts` (end to end with real keys: a member's private key opens the new wrap, that key opens the re-sealed rows and PDF, the old key opens nothing, the new recovery code works), `crypto-routes.test.ts`, `apartments-routes.test.ts` (stale key), `crypto-provider.test.tsx` (silent re-key, stable identity), `household-settings.test.tsx`.
