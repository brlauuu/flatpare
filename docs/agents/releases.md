# Versioning and releases

Full reference. The rules for this area are in AGENTS.md (always loaded); this file holds the detail, the measurements and the history behind them.

- **The version lives in `package.json` only** (`package-lock.json` mirrors it in its two root `version` fields — edit those by hand; `npm install --package-lock-only` on a local npm 10 rewrites unrelated entries, see Dependency maintenance). No other file quotes it. There were no tags or releases before 0.2.0 (2026-10-02); everything earlier shipped untagged.
- **`CHANGELOG.md` is the release notes.** Every merged PR adds a line under `## Unreleased`, grouped Added / Changed / Fixed, ending with the issue or PR number. Write for the person using the app, not the person reading the diff.
- **After every merged PR, cut a release** (decided 2026-10-02): graduate Unreleased into `## X.Y.Z — YYYY-MM-DD`, bump the version, open `release: cut X.Y.Z` as its own PR, and tag `vX.Y.Z` from `main` only after that PR is merged and CI is green. **Minor** for a new user-visible capability or an additive migration; **patch** for fixes, dependencies, docs and internal work. A breaking change on this 0.x line is still a question for the owner, never a silent bump. `/release` follows these steps.
- **1.0.0 is cut when Flatpare leaves the beta** (decided 2026-10-27). The hosted deployment launches as a beta on 0.x, and opening sign-ups during it is still a 0.x release. What 1.0.0 requires (billing live, the beta copy removed) is the checklist on #232.
- **Pushing a release tag deploys it** (#321): `.github/workflows/deploy.yml` runs on `v*`, refuses a tag whose commit is not on `main` or that does not match `package.json`, runs `vercel deploy --prod` on exactly that commit, and then checks that flatpare.com mentions the version (through the release notice) and still registers Google sign-in. **A merge to `main` deploys nothing**; the release does. So the order in the release steps above matters: merge the release PR, wait for green CI, push the tag — and the tag is the deploy. `gh release create vX.Y.Z --notes-file <section>` is still done by hand afterwards.
  - Vercel builds the uploaded source with the production environment, so `scripts/vercel-build.mjs` runs the migration preflights there: a release that cannot migrate fails its build, not the live site. **Releasing a migration applies it to production.**
  - **Why a tag can be trusted:** `main` is protected (2026-10-03) — the `test` check must pass on an up-to-date branch, changes go through PRs only, no force pushes or deletion, and the rule binds admins too. Every commit on `main` is one CI passed, and the workflow deploys nothing else.
  - **Vercel's Git integration is off** (`vercel.json`, `git.deploymentEnabled: false`), so neither merges nor PRs deploy. Do not turn it back on to "simplify": preview builds receive `TURSO_DATABASE_URL` and would migrate production (#212); #320 briefly ran it for `main` only, superseded by this.
  - It needs the **`VERCEL_TOKEN`** repository secret; without it the run fails loudly and names the fix. The org and project ids in the workflow are identifiers, not credentials. To redeploy a release (after rotating the token, say), run the workflow by hand with the tag: `gh workflow run deploy.yml -f tag=vX.Y.Z`.
- **`brlauuu.github.io/flatpare` is a redirect to flatpare.com** (#325): `github-pages/index.html` and an identical `404.html`, so every path under `/flatpare/` lands on the landing page. `.github/workflows/pages.yml` publishes exactly that directory (Pages source: GitHub Actions) when it changes on `main`; nothing else in the repository becomes a website. It has nothing to do with the app's deploy. If the domain moves, change both files.
