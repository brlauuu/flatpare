# Architecture checks (enola)

Full reference, moved verbatim from AGENTS.md. The always-on rules for this area are summarised in AGENTS.md; this file holds the detail, the measurements and the history behind them.

- The baseline is pinned at the E1 merge (`dad02e1`), which **accepts one module
  cycle**: `src/auth.ts` imports `@/lib/household`, and `src/lib/session.ts`
  imports `@/auth`. At file level the graph is acyclic — that split exists
  deliberately, to stop `auth.ts` and `household.ts` importing each other — but
  at directory-module level `src` and `src/lib` now point both ways. It replaced
  a pre-existing cycle inside `src/lib`, so it is a lateral trade, and
  `src/auth.ts` lives at the top level because Auth.js expects it there.
- **Grade architectural changes with `enola check --fail-on=cycles`.** Only
  findings that are *new* against the pinned baseline fail, so the accepted cycle
  above passes and a newly introduced one does not.
- The session Stop hook enforces this locally: `~/.claude/hooks/enola-stop-if-changed.sh`
  runs `enola check --fail-on=cycles` when the findings change, and appends a
  POLICY VIOLATION notice when a new cycle appears. Verified by introducing a
  deliberate `src/lib -> src/app` cycle and watching the gate exit 1.
- **Known limit, measured not assumed:** the cycles explainer only catches cycles
  between coarse modules. A deliberate file-level loop *within* `src/lib`
  (`src/lib/db` <-> `src/lib/pathname`) was reported as PASS with no cycle
  finding. So the gate catches cross-area cycles, not fine-grained ones inside a
  directory.
- CI does not run enola (the binary is not installed there), so this is a
  machine-local gate, not a repository one. That is the remaining gap.
- Re-pin with `enola baseline pin` after a deliberate structural change, or the
  next run grades against a stale architecture.
- **`.enola/` is gitignored, so the baseline is per-machine and a re-pin does
  NOT travel in a PR.** Each person's gate grades against whatever they last
  pinned themselves, and nothing reminds them. That is how the baseline came to
  sit five days and two epics behind (#258) with no visible symptom — the gate
  kept passing, because it was comparing against the wrong thing. If you clone
  fresh, or have not pinned in a while, pin before trusting a PASS. The re-pin
  entries below are therefore a record of what the architecture was *meant* to
  look like at each point, not a shared artefact you inherit.
- E2 re-pinned the baseline after adding `src/lib/crypto/**`, `src/components/crypto/**`, `src/lib/api-error.ts`, `src/lib/api-route.ts`, `src/lib/member-keys.ts`, `src/lib/invitations.ts` and the `/api/crypto`, `/api/invitations`, `/api/household` route trees. The intended layering is `src/components/crypto → src/lib/crypto` (and types only from `src/lib/member-keys` / `src/lib/encryption-mode`); `src/lib/crypto` imports **exactly one thing** from the app: `import type { EncryptionMode }` in `envelope.ts` (#259 measured it — that is the only `@/`-prefixed import in the whole tree, and it is type-only, so at runtime the tree really is a leaf). Do not let a *value* import appear there; the ESLint layering rule does not police direction, so this one is on you.
- E3 re-pinned the baseline after replacing the data layer: `src/lib/household-data/**`, `src/components/household-data/**`, `src/lib/data-rows.ts`, `src/lib/process-schemas.ts`, `src/lib/crypto/bytes.ts`, the `/api/process`, `/api/files`, `/api/ratings` route trees, and the removal of `src/lib/map-embed.ts`, `src/lib/short-code.ts`, `src/components/apartment-map.tsx` and the `/api/geocode`, `/api/settings`, `/api/parse-pdf` trees. Intended layering: `src/components/household-data → src/lib/household-data → src/lib/crypto`; `src/lib/household-data` imports nothing from `src/app` or `src/components`; routes no longer import `src/lib/household-data/wire` at all — **zero do** (#259). The wire types reach them through `src/lib/data-rows.ts`, which is the one hop that reads that module. The layering intent is unchanged; the path is one hop longer than this line used to claim.

Accepted for the same reason as the E1/E2 cycle — the split is deliberate and the graph stays acyclic at file level — so it is a lateral trade, not a new one; record it here so the next reader doesn't re-litigate it.
  - Two other findings surfaced mid-epic and were fixed, not accepted. First, a cycle between `src/components/crypto` and `src/components/household-data`: `crypto-gate.tsx` mounted the household-data store while the store imported the crypto context. Fixed by moving the `HouseholdDataProvider` mount into the four signed-in layouts and the identity derivation into `resolveHouseholdIdentity` (`src/lib/session.ts`); `src/components/crypto` must import nothing from `src/components/household-data` going forward. Fixed by moving it to `src/components/household-data/use-apartment-pager.ts` — nothing under `src/lib/` may import from `@/components`; a hook that reads the store belongs beside the store, not in `src/lib`.
  - E4 re-pinned the baseline after adding `src/lib/safe-url.ts`, `src/lib/log-scrub.ts`, `src/lib/rate-limit.ts` and `src/lib/unique-constraint.ts`. The first three are leaves by design: `safe-url` and `log-scrub` import nothing at all, `rate-limit` imports only `@/lib/db` and `@/lib/api-error`. `unique-constraint` exists specifically because `src/auth.ts` cannot import `@/lib/api-route` (which reaches back to `@/auth` via `@/lib/session`) — if you need a shared helper in `src/auth.ts`, put it in a leaf, do not import the route layer.
  - Four standing findings are the design working as intended, not defects, and enola reports but does not fail them: `HouseholdDataProvider`'s cyclomatic complexity (the single-file store the plan specified), and the fan-in on `parseBody` / `requireMember` (every data route calls both by design). E5 added the fourth: fan-in on `useHouseholdData` (8 dependents). It is the single store the E3 plan specified and every page reading it is the point — the alternative, a separate `LimitsContext` with its own provider and prop path through all four layouts, would exist only to lower an advisory number. `ApartmentsPage` and `HouseholdSettings` complexity also rose (33→36, 27→31) with the conditional counters; same category, same verdict. **File length is the same kind of advisory**: `household-data-provider.tsx` is 601 lines against a 500-line flag — the single-file store the plan specified — and `migrate.test.ts` (652) and `parse-pdf.test.ts` (512) also exceed it. Long test files are not a defect; splitting them to satisfy a line count would scatter one subject across several files for no reader's benefit. Re-raised and re-closed in #259.
  - **E6/E7 re-pinned the baseline (2026-09-16, #258) at `5ffae73`** — it had been stuck at 2026-09-09, before Stripe shipped, so billing was being graded against an architecture that predated it. New modules: `src/lib/stripe.ts`, `src/lib/billing.ts`, `src/lib/billing-gate.ts`, `src/app/api/billing/**`, `src/app/billing/**` and `src/app/_components/`. Intended layering, all verified at the pin:
    - `src/lib/stripe.ts` is a **leaf** — it imports the Stripe SDK and nothing from the app. Keep it that way; it holds `PRICE_CHF_CENTS`, and a module that only names the price has no business reaching into the app.
    - `src/lib/billing.ts` imports `@/lib/db`, the schema, `@/lib/api-error` and `@/lib/unique-constraint` — the E4 leaf, for the same reason it exists.
    - `src/lib/billing-gate.ts` imports `@/lib/billing` and `next/navigation`, nothing else. It is deliberately thin: the decision it encodes (`granted === 0`, never `remaining === 0`) is the whole module.
    - `src/app/billing/**` sits **outside** the shared signed-in layout, so it does not depend on `CryptoGate` or the household store. That is a product requirement (buying must not require unlocking a key), and it shows up here as `src/app/billing` having no edge to `src/components/crypto`.
  - **Reading the cycle finding**: enola renders it as `src -> src/lib -> src/lib/crypto -> src/lib/db -> src/lib/household-data -> src`. That is the *membership* of one strongly-connected component, not a literal chain of imports — `src/lib/crypto` does **not** import `@/lib/db`, measured in #259. Do not go looking for that edge; it is not there.
