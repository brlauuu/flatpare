# Apartment credits (E6)

Full reference. The rules for this area are in `.claude/rules/apartment-credits.md` (loaded when working on its files), with anything cross-cutting in AGENTS.md; this file holds the detail, the measurements and the history behind them.

- **What shipped and what did not.** Checkout, the webhook grant, the event-id idempotency key, the credit ledger and the purchase gate are all in `main` and tested — the heading used to say "partial" without saying of what (#263). Outstanding, and each is a *decision* rather than missing code:
  - **The two spend holes the quota does not close** (measured 2026-09-09, on #188). Adding a location re-runs distances for every apartment (~$0.40 per location); `runMaintenance("distances")` and Reprocess re-run everything (~$2.00 per click at 40×5). Since #413 Reprocess costs one credit and Recompute all one credit per run, so both are bounded by what was bought; adding or changing a location stays free (decided on #413). A modified client can still skip the charge, see Processing and credits (#413).
    - **Decided 2026-09-16: ship as is, with no rate limit.** `PROCESS_RATE_LIMIT_PER_HOUR` stays unset on the hosted deployment on purpose. The reasoning is that real revenue and real usage are unknown until the product is actually running, and a ceiling guessed in advance is as likely to frustrate a paying customer as to save money. CHF 5 holds for the first customers; the price and this decision get revisited with real numbers, and a change would apply to new customers rather than retroactively.
    - So this is **an accepted cost, not an oversight**. Do not "fix" it by setting the variable, and do not re-raise it in an audit without new usage data. The mechanism is built and one env var away if the numbers say otherwise.
  - **Refunds are manual.** There is no refund function (the last one, an internal rollback, went with #413) and no operator path or negative-credit row.
  - **Running out is a hard block**, not a soft warning at 35 of 40. The spec left that open; nothing warns before the cap.
  - Merchant-of-record posture is #241, still open.
- **Credits are one shared household pool (decided 2026-09-29, #294).** Any member can add an apartment and spend a credit, and any member can buy more; `POST /api/apartments` and `POST /api/billing/checkout` check membership (`requireMember`), never role. There is **no owner-only rule and no per-member budget**, on purpose: the landing page sells 10 people and 40 apartments per household with no per-person share, two people collecting listings together is the core use case, the owner already controls who is in (only they invite, and they can remove), and a per-member counter would put who-adds-how-much into plaintext the server does not hold today. Do not add a role check to apartment creation or to the charges; `process-routes.test.ts` pins a non-owner member spending from the pool (#413 moved it there with the spending). If a real household asks for control, the next step is a per-member on/off switch set by the owner, not budgets. Showing the remaining balance to every member is #305.
- **The remaining balance is shown to every member (#305)**, by `CreditBalance` (`src/components/credit-balance.tsx`) on the apartments page (its empty state included, which is a separate branch) and in the Household page's own **Credits** section (`HouseholdCredits`, `src/components/household-credits.tsx`, with the credit-code form; 2026-11-14, it used to sit under Members and read as part of the member list). "Buy more" / "Redeem a code" is an outline button (`cn(buttonVariants(...))` on a `Link`; without `cn` the base `border-transparent` wins and the frame loses two sides). It reads `useHouseholdData().credits`, which the store fetches from `GET /api/billing/status` beside each load and again after every call that may charge (a first processing, a reprocess, a recompute), **refused or not** — a 402 means another member spent the last credit, and the number on screen is what said there was one. The wording is "left to process" since #413. `credits` is **null when billing is off**, and the component then renders nothing; both pages have a test asserting the absence. The number is orange at 5 to 1 and red at 0 (`LOW_CREDITS`), with screen-reader text so the warning does not rest on colour. **"Buy more" shows at every balance**, not only at zero (decided on #305).
- **The checkout waits for the total to grow, not to be above zero.** `CheckoutPanel` takes `grantedAtStart` from the billing page and polls for `granted > grantedAtStart`. Polling for `granted > 0` was correct only for a first purchase: a household topping up already holds credits, so it was sent back to the app two seconds into the payment form. Found and fixed in #305, when the top-up path first got a link.
- **Two ceilings apply to adding an apartment, and they mean different things:**
  - `MAX_APARTMENTS` (E5) — how many rows you may **hold** at once.
  - Credits (`households.apartment_credits_granted` vs `apartments_ever_added`) — how many processings you may **ever pay for** (#413; the column name predates it). `apartments_ever_added` is **monotonic and never decremented by a delete**, because processing is what costs money (a Gemini extraction, a geocode, two distance elements per saved location) while holding costs a few hundred bytes of ciphertext. The landing page sells exactly this; `src/lib/__tests__/billing.test.ts` pins it.
- **Taking money is off unless `STRIPE_SECRET_KEY` is set** (`billingEnabled()`, `src/lib/billing.ts`). **Counting credits is a separate question since #492** (`creditsEnabled()`): on whenever Stripe is configured, and also with `FLATPARE_CREDITS=on`, so beta testers spend credits the way they will after launch before the deployment can take money. Unset, empty or `off` leaves it to Stripe, so a self-hoster is never counted; any other value throws `CreditsConfigError`. With counting off, `apartments_ever_added` is not even incremented, so turning it on later does not present anyone with a bill for their history (and testers who processed while it was off keep their full grant: no backfill, decided on #492).
  - The original rule was "a deployment that cannot take money must not enforce a paywall — there would be no way to lift it". #492 keeps its point by giving the counted-but-not-purchasable state its own way to lift the limit: **credit codes**, never a checkout. `readCreditBalance` answers `enabled` (counted) and `purchasable` (Stripe); the client's `Credits` carries `purchasable`.
  - **With `purchasable` false**: the purchase gate (`requirePurchase`) never redirects, `/billing` redirects to `/apartments`, and every "Buy more" link (`CreditBalance`, `ProcessingNotice`) becomes "Redeem a code", linking to `/household#redeem-code`. Tests pin each.
- **Credit codes (#492)**: `credit_codes` (code, label, credits, max_uses, uses, expires_at, revoked_at) and `credit_code_redemptions` (code_id, household_id; primary key on both), migration 0029, plaintext host-side records like beta passes. `src/lib/credit-codes.ts` holds the store; `POST /api/billing/redeem` (any member, `requireMember`; 404 when credits are not counted) redeems one; `RedeemCreditCode` (`src/components/redeem-credit-code.tsx`) is the form on the Household page, shown wherever credits are counted (it stays after launch, for gifts and make-goods), with a beta hint only while nothing can be bought.
  - **Claim, then use, then grant**, each one statement (#225): the redemption insert (`ON CONFLICT DO NOTHING`) is the once-per-household claim; the guarded `UPDATE ... WHERE uses < max_uses` (and not revoked, not expired) consumes a use, and a claim whose use fails is deleted again so it never blocks a later valid attempt; `grantApartmentCredits` runs last. 8-way tests pin exactly 3 of 8 households through a 3-use code and one grant when a household races itself.
  - **The code is never echoed or logged**: refusals are two fixed messages (`That code is not valid.` for unknown, malformed, revoked, expired or used up alike; `Your household has already used this code.`), and the route logs an unexpected error's class only (`scrubbedErrorLine`), since a failed query's error carries its parameters.
  - Minted with `node scripts/credit-code.mjs create [--credits 40] [--label L] [--max-uses N] [--expires-in-days N]`, plus `list` and `revoke <code>`. Like `beta-pass.mjs` it loads `.env.local` and prints the database before touching it. Revoking stops the code; credits already added stay. Codes are 32 hex characters from `randomUUID` (122 bits), so guessing is not a way to free credits; input forgives spaces, dashes and capitals.
- **A credit is claimed, then spent** (#413): `chargeFirstProcessing` inserts the apartment into `apartment_charges` (insert-or-ignore) and only the call that wrote the row spends, by a guarded single-statement `UPDATE ... WHERE apartments_ever_added < apartment_credits_granted`; when nothing is left the claim is deleted and the call answers 402. Spending first and claiming second refused concurrent calls for the same apartment whenever fewer credits than calls were left (measured). 8-way tests pin one credit for one apartment and exactly 3 for 3 credits. **Do not wrap this in `db.transaction`** — see #225.
