# Processing and credits (#413)

Full reference, moved verbatim from AGENTS.md. The always-on rules for this area are summarised in AGENTS.md; this file holds the detail, the measurements and the history behind them.

- **Creating an apartment is free; processing it spends the credit.** An apartment added by hand or from a link can be rated and described at no cost. Its first processing (its PDF read, or its address geocoded, whichever comes first) spends one credit; the other one is then free. Design decisions are the owner's comments on #413.
- **The server keys on the apartment id the request names** (`chargeFirstProcessing` in `src/lib/billing.ts`): `POST /api/process/parse-pdf` requires `apartmentId` (form field) and charges it just before the extraction, nothing when no AI is configured; `POST /api/process/geocode` takes an optional `apartmentId` and charges it before the call. A location of interest is geocoded without one, free. Distances never charge. A reprocess is `POST /api/apartments/:id/reprocess` (one credit every time, and records the apartment as charged so the calls that follow are free); Recompute all is `POST /api/billing/recompute` (one credit per run). Both no-ops when billing is off. The server cannot see an address, so a modified client could geocode without naming the apartment: accepted, see `docs/security-notes.md`.
- **The client names the apartment only on its first processing.** `runEnrichment` sends `apartmentId` only when `!processed`; retries, map upkeep (`planGeocodeMaintenance` plans only processed, current apartments) and the geocode after a PDF read go without it, so the app never spends a credit on its own.
- **Two envelope fields**: `processed` (absent in envelopes before #413 = true: their credit was spent at create) and `processedAddress` (the address the coordinates and distances belong to; absent = the address, when the envelope has coordinates). `planEnrichment(next)` geocodes only an address never geocoded (`processedAddress === null`).
- **A changed address is not geocoded again.** `deriveApartments` sets `addressChanged` and hides the view's coordinates and distances (the stored ones are kept, so changing it back restores them); the apartment page says so in the distance section and offers Reprocess. Never "fix" this by geocoding on edit: that is the free reprocess the owner decided against.
- **A PDF never overwrites what a member entered**: reading one for an apartment someone already described goes through `fillFromExtraction` (`src/lib/edited-fields.ts`), which fills only empty fields and marks the filled ones as edited, so a later reprocess keeps them too.
- **Out of credit is not an error.** A 402 leaves the apartment unprocessed with its address or PDF saved; `ProcessingNotice` on the apartment page says so, links to `/billing` and offers Process once a credit is there. On the add page a PDF refused for want of credit is kept unread (`notRead`) and saved unprocessed with its PDF. A processed apartment whose address could not be placed (a failed geocode, including the one after a reprocess, which clears the old coordinates first) gets a free "Try again" in the same notice, never Reprocess, which would charge again.
- **Links and PDFs on an existing apartment.** Paste link and a shared link add an unprocessed apartment (see Drafts, retired by #413). On the apartment page, **Attach PDF** stores the PDF and reads it, the first processing unless the address was processed already (then free); **Replace PDF** asks, then stores the new file only (decided on #413: replacing does not reprocess). Out of credit, an attached PDF stays unread and the notice offers Process. `attachPdf` in the store uploads under a fresh name (`pdfFileName(id, keyVersion, revision)`, `.r<12 hex>`), points the row at it, and only then deletes the old file through `DELETE /api/files`; a failed write deletes the new file instead. Blob refuses to overwrite a name, and the row must never point at bytes it cannot open.
- **The host can see who processes without paying, per household, not per member.** `process_usage` counts every process call (limit or not) and `credit_spends` records what each credit paid for (`first`, `reprocess`, `recompute`; written by `consumeApartmentCredit`, billing on only). `node scripts/usage-report.mjs [--days 30]` prints both side by side for each household with activity and marks a line `check` when PDF reads or geocodes run far ahead of the credits spent (`needsCheck` in `scripts/usage-report-lib.mjs`, loose on purpose); `--household <id>` gives that household day by day. Read-only, same database selection as `scripts/beta-pass.mjs`, so with `.env.local` it reads flatpare-dev, not production. Per household by decision (owner, #413): a per-member count would put who-does-what into plaintext, the posture #294 avoided. Both counts start with 0.27.0. It caps nothing; `PROCESS_RATE_LIMIT_PER_HOUR` is still the only cap.
- **People are told, in four places (#468)**, all five languages: the landing page's privacy list (`privacy.seesUsage`, pinned in `DISCLOSURES`), the guide's "What the server can see", one line under the sign-in card (`landing.signIn.privacyNote`, in `sign-in-dialog.tsx`, whose link closes the dialog onto `#privacy`), and `UsageNotice` (`src/components/usage-notice.tsx`), shown once in the shared signed-in layout to every member, existing ones included, dismissed per browser in `localStorage` (`flatpare_usage_notice_seen`; `capture:hero` pre-dismisses it). What they say: counts per household, never per person, never what was processed, and that flatpare.com reviews them against what was paid for. **A new count, or reading these per member, means changing all four.** The terms page (#474) lists the same counts under "Your data"; change it with the four.
- **The same report as a page and by email (#431).** `--html <file>` writes one self-contained page (the summary, check rows highlighted, and a daily chart per household of PDF reads with geocodes against credits spent, inline SVG, no script, nothing loaded from elsewhere); `--email <address>` sends a summary through Resend (the totals, the households to check with the reason, the ten most active; `renderEmail`) with the page attached as the full report (email clients drop SVG and `<style>`). The pure half (rule, shaping, page, email, cadence) is `scripts/usage-report-lib.mjs`, tested by `src/lib/__tests__/usage-report.test.ts`; one rule marks all three outputs. Pages go in `/reports/` (gitignored). **`.github/workflows/usage-report.yml` sends it on a schedule**: daily at 06:00 UTC, sending only when `USAGE_REPORT_CADENCE` (repository variable: `daily`, `weekly` = Mondays, `monthly` = the 1st) matches; unset sends nothing; Run workflow sends now. It reads production with a **read-only** Turso token (`USAGE_TURSO_DATABASE_URL`, `USAGE_TURSO_AUTH_TOKEN`), plus `RESEND_API_KEY`, the address and the sender as the secrets `USAGE_REPORT_EMAIL` and `EMAIL_FROM`. **The repository is public, so its Actions logs are too**: with `--html` or `--email` the script prints only the database host and the outcome, never a count, a household id or an error message, the job uploads no artifact, and the address is a secret because a step's env is printed in its log. Keep all three true. No `pull_request` trigger, so nobody without write access can run it with those secrets.
- **The buttons say what they cost** when billing is on: Reprocess's confirmation, Process "(1 credit)", Recompute all's description and confirmation. With billing off nothing mentions credits; tests pin both.
- **`ui_mode` is `"embedded_page"`, NOT `"embedded"`** — the latter was retired and the live API rejects it outright ("The ui_mode value `embedded` is no longer supported"). Vercel's own Stripe guide still shows the old value, which is where it came from, so copying a snippet from there reintroduces it. This is API drift a mock cannot catch: the unit tests stub `checkout.sessions.create`, so the shape is only validated against the real API — by `e2e/billing.spec.ts` or by a live checkout. Same class as the missing `tax_code` and the VAT-on-top defect; all three are #238.
- **Stripe: CHF 5, one-time, embedded Checkout.** `mode: "payment"` with inline `price_data` (`src/lib/stripe.ts` holds `PRICE_CHF_CENTS`), **never** `subscription`. The amount lives in code beside the landing-page copy that advertises it, with tests on both, rather than in a dashboard Price that can drift silently.
- **`POST /api/billing/webhook` is the ONLY thing that grants credits** — not the checkout route, not the client, not a redirect. `redirect_on_completion: "never"` means there is no return URL to forge; the page polls `GET /api/billing/status` and waits for the webhook's grant.
- **That webhook is the one endpoint in the app that is unauthenticated by design.** Stripe has no session, so `src/proxy.ts` allow-lists it explicitly and its signature is its only authentication. Two rules are absolute: read the **raw** body (`req.text()`, never `req.json()` — the signature covers exact bytes), and verify before trusting anything. Its tests sign real payloads with `Stripe.webhooks.generateTestHeaderString`, including a tampered-after-signing case; **do not mock `constructEvent`**, that would test nothing.
- **Idempotency is the `payments` primary key**, which is the Stripe **event id**. Stripe delivers at least once, so a redelivery must be a no-op rather than a second 40 credits. `recordPaymentOnce` inserts before granting: dying between the two leaves the customer short and the ledger honest, which is visible and fixable, whereas the other order double-grants silently.
- **The purchase gate keys on `granted === 0`, never `remaining === 0`** (`src/lib/billing-gate.ts`). A household that never bought has no data, so gating it is safe; one that bought and spent its credits **owns apartments**, and gating it would lock a paying customer out of their own search — which under E2EE nobody could undo. Running out of credits means "no new apartments", never "no access".
- `/billing` sits **outside** the shared signed-in layout on purpose: that mounts `CryptoGate`, and buying should not require unlocking a key the user may not have set up yet.
