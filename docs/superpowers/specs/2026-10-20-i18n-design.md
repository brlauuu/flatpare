# Five languages (#288) — design

Decided on #288 (2026-09-20, 2026-10-03) and in the session of 2026-10-20.

## Scope

- **English, German, French, Italian, Spanish**, all five at once. Every
  string: the app, the landing page, the guide, the emails. A visible
  language selector, not a hidden setting.
- **Swiss conventions**: German written the Swiss way (`ss`, never `ß`),
  French and Italian in Swiss usage, numbers and dates formatted as
  `de-CH` / `fr-CH` / `it-CH`. Spanish as in Spain (`es-ES`). English stays
  `en`.
- **The landing page is translated**, and its copy rules hold in every
  language, tested per language: the privacy claim says the same thing, no
  unqualified "zero-knowledge", never "open source", every price `CHF 5`.
- **The PDF prompt** (`src/lib/parse-pdf.ts`) learns French, Italian and
  Spanish listing vocabulary beside the German, and writes the free-text
  `summary` in the uploader's language.
- **Native-speaker review after it is live**: a packet per language, the
  legally loaded sentences first. Corrections arrive as follow-up PRs.

## Decisions

### Same URLs; the language is a cookie

`flatpare.com/apartments` stays `flatpare.com/apartments` in every language.
`next-intl` is used **without i18n routing**: `src/i18n/request.ts` resolves
the locale per request and nothing about routes, `src/proxy.ts`, Auth.js
callbacks, `/beta/<code>` links or email links changes.

Resolution order, first match wins:

1. the `flatpare_locale` cookie, when it names a supported locale;
2. signed in, no cookie: `users.locale` from the account (a new device);
3. the `Accept-Language` header, negotiated against the five;
4. `en`.

Trade-off accepted: search engines index one language of the landing page.

### The choice is also saved on the account

Choosing a language sets the cookie and, when signed in, `users.locale`
(migration 0023, nullable, additive, no preflight). So it follows a person
to a new device, and an email sent **to** a member (removed from a
household) goes out in the language they chose. An email to someone who
has no account (an invitation) goes out in the sender's language.

`users.locale` is account data in plaintext, like `users.name` (#327) — it
is a preference about the interface, not household data, and the server
needs it to pick an email's language.

### Messages

- One catalogue per locale, `messages/<locale>.json`, namespaced by area
  (`nav`, `apartments`, `crypto`, `landing`, …). English is the source.
- **Types come from English**: `AppConfig.Messages` is `typeof en`, so a
  missing key or a missing placeholder argument is a compile error.
- **A test keeps the catalogues in step**: every locale has exactly the
  English keys, and every message has the same ICU placeholders as its
  English one. A translation that drops `{count}` fails CI, not a user.
- Formatting (dates, numbers) goes through `next-intl`'s formatter with the
  regional tag, never `toLocaleString()` with no argument.
- `<html lang>` comes from the active locale (`de-CH`, …), so a screen reader
  reads German as German.

### Server-sent messages

Errors the server returns as text and the UI shows (for example the display
name's validation) stay English on the wire. The client maps the known ones
to catalogue keys; an unknown one is shown as sent. Moving every API error to
a code is not part of #288.

### Tests

Most component tests assert English text. `src/test-setup.ts` gives every
test an English `next-intl` context, so they keep passing unchanged and a
missing provider is never the reason a test fails. Tests about language use
the real provider with a chosen locale.

## The five PRs

Each one ships and is released on its own.

1. **Setup + selector + the app.** `next-intl`, locale resolution, the
   selector (nav bar, landing page nav, sign-in card), the account column,
   `<html lang>`, the catalogue test, and every string under `src/app/(app)`,
   `src/components`, `/billing`, `/invitations`, the crypto screens and the
   sign-in card — in all five languages. The landing page and the guide stay
   English until their PRs.
2. **The landing page**, with per-locale copy-rule tests.
3. **The guide**: `src/content/guide.<locale>.md`, chosen by locale.
4. **The emails**: templates per locale; recipient's `users.locale` when
   there is a recipient account, the sender's language otherwise.
5. **The PDF prompt**: French, Italian, Spanish recognition patterns; the
   `summary` in the uploader's language, passed with the request. A summary
   is stored in the envelope, so in a mixed-language household the others
   see it in the uploader's language — accepted on #288.
